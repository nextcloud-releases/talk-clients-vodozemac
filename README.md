# talk-clients-vodozemac

Swift and Kotlin bindings of [vodozemac](https://github.com/matrix-org/vodozemac) for the key exchange of end-to-end encrypted calls in Nextcloud Talk. It replaces libolm (OLMKit) in Talk iOS, where libolm is deprecated and no longer builds with current Xcode, and provides the same API to Talk Android. It stays compatible with the web client, which uses libolm through `@matrix-org/olm`.

## What it provides

The crate in `src/lib.rs` wraps only what the Talk key exchange (spreed `src/utils/e2ee/encryption.js`) needs:

| Swift | |
| --- | --- |
| `VodozemacAccount()` | New Olm account |
| `identityKey()`, `createOneTimeKey()` | Keys sent in `encryption.start` |
| `createOutboundSession(theirIdentityKey:theirOneTimeKey:)` | Session of the side receiving `encryption.start` |
| `createInboundSession(preKeyMessage:)` | Session of the side that sent it, together with the decrypted message |
| `VodozemacSession.encrypt(plaintext:)`, `decrypt(message:)` | |

| Kotlin (`com.nextcloud.talk.olm`) | |
| --- | --- |
| `VodozemacAccount()` | New Olm account |
| `identityKey()`, `createOneTimeKey()` | Keys sent in `encryption.start` |
| `createOutboundSession(theirIdentityKey, theirOneTimeKey)` | Session of the side receiving `encryption.start` |
| `createInboundSession(preKeyMessage)` | Session of the side that sent it, together with the decrypted message |
| `VodozemacSession.encrypt(plaintext)`, `decrypt(message)` | |

Errors are thrown as `VodozemacError` (Swift) or `VodozemacException` (Kotlin).

Sessions use `SessionConfig::version_1()`, the only version libolm supports. `createInboundSession` returns the plaintext because vodozemac decrypts the pre-key message while creating the session and cannot decrypt it again.

The Swift bindings in `swift/Sources/TalkOlm` and the Kotlin bindings in `android/lib/src/main/kotlin` are generated by UniFFI and committed, since Swift Package Manager builds from the repository and the `generated` CI job checks them. `Package.swift` combines the Swift bindings with `TalkOlmFFI.xcframework` (arm64 device and simulator, iOS 16+). The Gradle project in `android` combines the Kotlin bindings with `libtalk_olm.so` for arm64-v8a, armeabi-v7a, x86_64 and x86 (Android 8.0+) into an AAR that depends on [JNA](https://github.com/java-native-access/jna).

## Using the Android AAR

The release workflow attaches the AAR to the GitHub release, and `jitpack.yml` makes [JitPack](https://jitpack.io) serve it for the tag without building anything:

```kotlin
repositories {
    maven { url = uri("https://jitpack.io") }
}

dependencies {
    implementation("com.github.nextcloud-releases:talk-clients-vodozemac:<version>")
}
```

## Building

[rustup](https://rustup.rs) installs the toolchain from `rust-toolchain.toml`. The XCFramework needs macOS with Xcode.

```sh
./scripts/generate-bindings.sh   # after any API change, commit the result
./scripts/build-xcframework.sh   # build/TalkOlmFFI.xcframework(.zip), prints the checksum
./scripts/build-android.sh       # android/lib/build/outputs/aar/lib-release.aar
```

The AAR needs [cargo-ndk](https://github.com/bbqsrc/cargo-ndk), an NDK (r28 or newer, found through `ANDROID_NDK_HOME` or the SDK) and Gradle 9.

## Tests

```sh
cargo test

# Key exchange against @matrix-org/olm, with each side starting once
cargo build --example interop_peer
npm ci --prefix interop
node interop/interop.mjs target/debug/examples/interop_peer

# Swift tests against the local XCFramework, needs the iOS 26.5 simulator runtime (xcodebuild -downloadPlatform iOS)
./scripts/build-xcframework.sh
TALK_OLM_LOCAL_BUILD=1 xcodebuild test -scheme TalkOlm -destination "platform=iOS Simulator,name=iPhone 17,OS=26.5"

# Kotlin tests on the JVM against the host library from target/release (or JNA_LIBRARY_PATH), no device needed
./scripts/generate-bindings.sh
gradle -p android :lib:test
```

CI runs all of these, checks that the generated bindings and `THIRD_PARTY_LICENSES.md` are up to date, and runs the REUSE compliance check.

## Releasing

Run the **Release** workflow with a version such as `0.1.0`. It uploads the XCFramework, the AAR and its POM to a GitHub release and tags a commit that sets the XCFramework URL and checksum in `Package.swift`. `main` keeps the placeholder, so use the package by version. JitPack builds the tag on first request by installing the released AAR.

## Updating vodozemac

Change the pinned version in `Cargo.toml`, run `cargo update -p vodozemac` and the tests, then regenerate:

```sh
./scripts/generate-bindings.sh
./scripts/generate-licenses.sh   # needs: cargo install --locked cargo-about --features cli
```
